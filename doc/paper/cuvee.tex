\begin{abstract}
\cuvee{} proves the safety of C programs with loops without inferring loop invariants.
Each loop is summarized by a \ac{TEQ}, which describes the sequences of values that
the variables take in the iterations. A database of lemmas, proved in Lean, rewrites these equations into closed forms, such as counters, sums, and arrays filled with values.
Goals that remain after rewriting are encoded in first-order logic and passed to Z3.
\cuvee{} does not search for counterexamples: it reports a violation only when rewriting refutes a goal.
It proves 219 safe tasks of ReachSafety-Arrays, against 68 for the best competing participant of
SV-COMP~2026 in the official results, and it reports no wrong results, also with the fallback to Z3.

\emph{Note:} This paper was generated with AI; see the AI Declaration. Its purpose is only to preview
the tool for the competition.
\end{abstract}

\section{Verification Approach}

The difficult part of the verification of loops is to find inductive invariants. Invariants describe the
state at the loop head. However, the reasons why a program is correct are often easier to state about the
whole computation of the loop: \emph{the array is a sequence of stores at the positions $0, \dots, n-1$}, or
\emph{the variable is the sum of the elements read so far}. \cuvee{} follows this view, as does loop
acceleration, which characterizes the transitive closure of a loop, recently also for loops on
arrays~\cite{frohn-arrays}. \cuvee{} represents the
computation of each loop by \acp{TEQ} and proves goals by rewriting with a database of lemmas
about such traces. The approach is described in detail in~\cite{teq}; we summarize it here.

\paragraph{Trace Equation Systems.}
\cuvee{} symbolically executes each function and inlines the calls, which must be of functions without a
contract. A loop that runs $n$ times is
replaced by a system of equations over \emph{traces}, sequences of values:
\begin{itemize}
\item a synthetic counter $K = \code{counter}(0, 1, n)$ of the iterations;
\item for each modified variable $x$ that reads no variable that reads it, an equation
  \[X = \code{trace}(x_0, \code{for } \lf{K}, \lf{Y}, \dots \code{ do } x, k, y, \dots \Rightarrow u).\]
  The update $u$ has one guarded case per path through the body, and $\lf{Y}$ is the trace of another
  variable without its last value; variables that read each other, a strongly connected component of the
  read relation, get one trace of several accumulators;
\item the iteration constraint $\code{invs}(\code{for } \dots \code{ check } \dots \Rightarrow
  \varphi)$, which states that each iteration ran with a true loop test along one of these paths;
\item the exit condition, the negated loop test on the values after the last iteration, which
  bounds the number $n$ of iterations from the other side.
\end{itemize}
The variable then has the value $\code{current}(X)$ after the loop. Nondeterministic values become lists
of choices, one value per iteration. The system is sound and relatively complete: it describes exactly the reachable states after the
loop~\cite{teq}. Figure~\ref{fig:example} shows the \ac{TEQ} of a loop that fills an array.

\paragraph{Rewriting with lemmas.}
\cuvee{} does not compute fixpoints or interpolants. Instead, its simplifier rewrites the equations with
lemmas of two kinds.
\begin{itemize}
\item \emph{Introduction rules} recognize a fragment of a computation and name it. For example,
  \[\code{trace}(i, \code{for } \lf{\code{counter}(0, 1, n)} \code{ do } x, k \Rightarrow x + c)
    \lemeq \code{counter}(i, c, n)\]
  turns the trace $I$ into $\code{counter}(0, 1, n)$, and the definition of \code{stores}, used as a rule,
  \[\code{trace}(a, \code{for } \mathit{Ks}, \mathit{Vs} \code{ do } b, k, v \Rightarrow b[k := v])
    \lemeq \code{stores}(a, \mathit{Ks}, \mathit{Vs})\]
  turns $A$ into the stores of zeros at the positions $\lf{I}$, where the matcher synthesizes the trace
  $\mathit{Vs}$ of the stored values.
\item \emph{Acceleration rules} evaluate observers of these functions. For example, the last value of a
  counter is, for $n \ge 0$,
  \[\code{current}(\code{counter}(i, c, n)) \lemeq i + n \cdot c,\]
  the iteration constraint of a loop up to a bound $m \ge 0$ is
  \[\code{invs}(\code{for } \lf{\code{counter}(0, 1, n)} \code{ check } k \Rightarrow k < m) \lemeq n \le m,\]
  and a read of the stores yields the value stored last at the position, or the initial one:
  \begin{align*}
    \code{current}(\code{stores}(a, \mathit{Ks}, \mathit{Vs}))[k] \lemeq{}
      & \textbf{if } \code{occurs}(k, \mathit{Ks})\\
      & \textbf{then } \code{earlier}(\code{indexof}(k, \mathit{Ks}), \mathit{Vs})\\
      & \textbf{else } a[k].
  \end{align*}
\end{itemize}
In the example, eleven rule applications close the goal.
The database contains 279 lemmas in nine modules over the definitions of a core module: aggregation
(sums, counts, minima, maxima, and bitwise aggregates, over multisets), arithmetic, arrays, counters,
search, sorting, strided stores, unsigned arithmetic, and series (closed forms of power sums and
geometric sequences). The order of the modules is the order in which rules are tried; for SV-COMP,
\cuvee{} loads all of them. All 279 lemmas have machine-checked proofs in Lean~4~\cite{lean4}. The matcher works modulo the binding structure of the
traces, modulo associativity and commutativity of $+$, and with higher-order patterns in Miller's fragment.
It also uses the context of each update, such as $0 \le k < n$ and the iteration constraints. Thus a lemma
applies to all loops that share its pattern, regardless of the names, order, and number of the other
variables.

Figure~\ref{fig:rules} shows how often the rules are used. Of the 459 tasks that \cuvee{} proves without
Z3, four rules, those about the counter of the iterations, occur in more than half, while 80 rules occur in
at most three tasks and 37 in a single one; 177 of the 279 lemmas of the database are used.

\paragraph{Fallback to SMT.}
The remaining goals are lowered into first-order logic, where each trace is a function of the
iteration index and each equation of a \ac{TEQ} a quantified characterization of its steps, and passed to
Z3~\cite{z3}. Functions of the database without a first-order definition are generalized, so a model
does not refute the program: the verdict is then \emph{unknown}.

\section{Software Architecture}

\cuvee{} is written in Scala~3 (about 26{,}000 lines). It is a pipeline of sources, transformations,
and sinks over a common core of logic and programs, with frontends for SMT-LIB, SV-LIB, Boogie, Dafny,
C, and SV-COMP task definitions. The C frontend handles integer programs with arrays, and reads ACSL
contracts and loop invariants. Signed integers are mathematical integers, since their overflow is
undefined, whereas unsigned arithmetic wraps around modulo $2^k$; nondeterministic values lie within
the range of their type. Arrays are values, also those allocated by \code{malloc} with a symbolic size.
The transformation \code{-teq} generates the goals and loads the lemma database, which is written in
Dafny syntax. The deduction engine \code{-prove} normalizes arithmetic into polynomials, simplifies
formulas under their context, and applies the lemmas. The context combines congruence closure, which keeps
terms in a canonical form, with a simplex for linear arithmetic over the rationals; it knows the definition
of division and remainders by literals, and bounds the remainders modulo $2^k$ of the unsigned arithmetic.
\code{-split} separates the goals, and \code{-fallback} lowers the remaining ones for Z3~4.16.

\paragraph{Strengths.}
\begin{itemize}
\item \emph{Arrays of unbounded size.} \cuvee{} proves more safe tasks of ReachSafety-Arrays than any other
  tool in the table: 219 with Z3 and 212 without, compared with 68 for the next tool. Most of them fill
  arrays with values that depend on the position or on earlier values, and their sizes are symbolic. The
  summaries do not depend on the number of iterations, so large or symbolic bounds do not matter.
\item \emph{No wrong results.} \cuvee{} reports no wrong result on all tasks, with or without the
  fallback.
  The lemmas of the database are proved in Lean~4, so the trusted base is mainly the translation into
  \acp{TEQ} and the deduction engine.
\item \emph{Explanations.} With \code{-rules}, \cuvee{} reports the lemmas that each proof uses, and
  a residual goal points to the lemma that is missing.
\item \emph{Incremental.} Rewriting also simplifies goals that it does not close. The remaining goals are
  often small enough for Z3: the fallback adds 7 proofs in Arrays and 11 in Loops, where rewriting
  eliminates the loops and Z3 solves the remaining arithmetic, such as products of bounded variables.
\end{itemize}

\paragraph{Weaknesses and limitations.}
\begin{itemize}
\item \emph{Few violations.} \cuvee{} does not search for counterexamples. It reports \emph{false} only
  if rewriting refutes a goal, without an abstraction on the way; a model of Z3 for a lowered goal is no
  counterexample, since the lowering generalizes. Thus it reports only 100 of the 329 unsafe tasks of both
  categories, and 96 with Z3, which uses up the time of some of them. Its witnesses carry no invariants
  and no values of a violation yet. In the official scoring, its results would therefore count as
  unconfirmed.
\item \emph{Machine integers.} Signed integers are mathematical integers, since their overflow is
  undefined behavior, which the tasks are meant to avoid. The wrap-around of unsigned integers is
  modeled by remainders modulo $2^k$, which make goals harder to close.
\item \emph{Coverage of the database.} A loop is summarized only if the database has a lemma for its shape.
  Loops whose summary needs only partial facts, such as bounds, minima, or maxima under conditional
  updates, are often not closed. In Loops, many tasks need nonlinear invariants, such as
  \code{nla-digbench}, or their loops are state machines. Here \cuvee{} without Z3 proves only 247 tasks,
  while the other tools prove 294 to 405. Each lemma fixes the shape of its left-hand side, so a loop that
  writes $s$ adjacent cells per iteration requires a fold for each $s$ (the database has them for
  $s \le 5$). Rewriting may also
  diverge, and such tasks end with \emph{rewriting does not terminate}.
\item \emph{Frontend.} \cuvee{} treats floating-point numbers as uninterpreted, rejects \code{goto} into
  code that falls through, and fails to parse some tasks, mostly because of structs. Bitwise operations are uninterpreted functions, except shifts by constants.
\item \emph{Limits of the fallback.} The first-order encoding does not cover every goal, e.g., when a goal
  has sequences that are not bound by a quantifier or lists nested more than twice. More often, Z3 does
  not answer in time.
\end{itemize}

Several lemmas of the database, among them those for conditional stores, sums with resets, and strided
stores, were found on the MonoCera benchmarks~\cite{monocera,monocera-artifact}.

\section{Tool Setup and Configuration}

\cuvee{} needs Java~21. The archive contains \code{cuvee.jar}, the script \code{Cuvee.sh}, and a Z3
binary, which the script puts on the path. The BenchExec tool-info module is \code{cuvee.py} (\code{benchexec.tools.cuvee}). It runs
\begin{center}
\small\code{./Cuvee.sh -svcomp -fallback -z3 -timeout 900000 [-arch 32|64] task.c}
\end{center}
where \code{-svcomp} stands for the options of SV-COMP: \code{-teq} with all modules of the lemma
database, \code{-prove -split -prove -split -prove}, and the witness (\code{-witness witness.yml}); and
\code{-arch} follows the data model of the task. Executions start in \code{main}, the entry point
(\code{-entry} selects another one); the other functions are checked where they are called. \cuvee{} answers
\emph{correct} if all goals are proved, \emph{incorrect} if a goal is refuted without abstraction, and
\emph{unknown} otherwise, which \code{cuvee.py} reports as \emph{true}, \emph{false}, and \emph{unknown}.
For C, it supports only the property \code{unreach-call}, and it participates in ReachSafety-Arrays and
ReachSafety-Loops. For SV-LIB scripts, it answers each \code{verify-call}.

\cuvee{} also participates in the SV-LIB categories CoreVerification and CTranslated of the property
\code{correct-tags}, with the same command on the script. The tool-info module reports \emph{false}
if a \code{verify-call} is answered \emph{incorrect}, and \emph{true} if all of them are answered
\emph{correct}. The archive also contains the licenses and a smoke test, which runs \code{-teq}, with
and without the fallback to Z3, and \code{-chc -z3}, the encoding into constrained Horn clauses, on a
safe and an unsafe C program and SV-LIB script each.

\section*{AI Declaration}

The theory of \acp{TEQ}, the translation of loops, the rewriting strategy, the matching of
traces, and the soundness argument, was fully worked out before this implementation~\cite{teq}. An
earlier implementation in Scala~2, with a lemma database of about 65 lemmas written in Boogie, produced
the results of that work. The present version of \cuvee{} started from a Scala~3 code base of about
3{,}500 lines written by the author: the core of logic and programs, the pipeline, and the frontends for
SMT-LIB and Dafny.

From there, coding agents (Claude Code with Claude Opus) carried out most of the implementation, under
the direction of the author, who set the design, decided the open questions, and reviewed the results;
819 of the 874 commits of the repository are co-authored by the agent. The agents wrote the generation of
\acp{TEQ}, the simplifier with its reasoning about the context, the rewriting with the database
and the matching of traces, the fallback to Z3, the encoding into constrained Horn clauses, the frontends
for Boogie, C with ACSL, SV-LIB, and SV-COMP task definitions, the tests, and the scripts of the
experiments. The code base grew to about 26{,}000 lines.

For the lemma database, the agents first ported the lemmas of the Boogie implementation to Dafny syntax,
added missing preconditions on bounds, and corrected some of them. They then extended the database to 279
lemmas in nine modules, mostly by analyzing the goals left open on the SV-COMP and MonoCera benchmarks
and writing lemmas for the missing loop shapes, under the review of the author. They also wrote the
formalization of the core definitions in Lean~4 and the proofs of all 279 lemmas.
The agents ran the experiments and drafted parts of this paper under the direction of the author.
