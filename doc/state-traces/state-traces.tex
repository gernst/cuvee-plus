\begin{abstract}
This note explains how the verifier Cuvée proves array programs without loop invariants, by three examples that
every reader of a verification paper knows: the initialization of an array, the element-wise exchange of two
arrays, and a binary search. A loop is represented by folds over its iterations whose results are \emph{traces}, the sequences of values of
the program variables at the loop head, one trace per group of variables that depend on each other, and the
verification condition is a first-order formula over traces. The formula
is proved by rewriting with a database of lemmas about traces, each a small fact about a loop shape (a counter, a
sequence of stores, a constant), under a context that keeps the facts of the goal. No invariant is written, and no
lemma is written for the first two programs. The note introduces the representation, the lemma database, and the
engine as the examples need them. The binary search has no closed form. It is proved from bounds, by a lemma about the bisection of an interval
as a whole, whose bounds are facts that hold wherever their term occurs. The note ends with what the examples do not show.
\end{abstract}

\section{The idea}

A verifier based on Hoare logic asks for an invariant of every loop. For the initialization of an array the invariant
is easy, \lstinline|forall k :: 0 <= k < i ==> a[k] == v|, but it is an input of the user and not a property of the
program, and for programs that compute something more involved it is where the effort goes. Trace equation systems
take another route. Instead of asking what holds at the loop head in every iteration, they ask what the loop
\emph{computes}: the values of the variables after $n$ iterations, as a function of the inputs and $n$. For a loop
that counts, that function is $i_0 + n$; for a loop that stores $v$ at positions $0, \ldots, n-1$, it is the array
with those positions set to $v$. Once the loop is summarized by such a function, the postcondition is a claim about
the function, and that claim is first-order.

The summary is obtained in two steps. Symbolic execution turns the loop into a \emph{trace}, a sequence of states,
defined recursively from the body: the state after an iteration is the body applied to the state before it. This is
mechanical and needs no insight. Then a rewrite engine applies lemmas from a database to the trace, each stating what a
particular shape of loop computes, until the trace has a closed form and the postcondition follows by arithmetic.
The insight sits in the database, written once; a new program is verified without a lemma of its own as long as its
loops are composed of shapes the database knows.

The first two examples below are such programs. The first shows the representation and the ordinary lemmas, the
second shows what happens when two variables of a loop depend on each other, which is where the approach needed
an idea that the paper on trace equation systems did not have. The third, a binary search, has no closed form: it
is proved from bounds, by a lemma about the whole loop that is not in the database yet, and shows where the database
ends.

\section{Array initialization}

\begin{lstlisting}
method init(n: int, v: int) returns (a: array<int, int>)
  requires 0 <= n
  ensures forall k: int :: 0 <= k < n ==> a[k] == v
{
  var i: int;
  i := 0;
  while i < n
  {
    a[i] := v;
    i := i + 1;
  }
}
\end{lstlisting}

Arrays here are total maps from integers to integers (the type \lstinline|array<int, int>|), so there is no bounds
check and \lstinline|a[i] := v| is the functional update $a[i := v]$. The run is
\begin{center}
\texttt{./Cuvee.sh -teq-state -prove examples/dafny/state/init.dfy}
\end{center}
where \texttt{-teq-state} produces the verification condition over traces and \texttt{-prove} runs the engine. The
output is empty: the goal is proved and therefore dropped.

\subsection{The verification condition}

Symbolic execution runs the method body on symbolic values, collecting the assumptions and checks of each path. The
loop is the only interesting statement. Its modified variables are $a$ and $i$; the index reads nothing, the array
reads the index, so the two are summarized separately, the array after the index. The condition produced for the
method is (with \texttt{-print dfy} in place of \texttt{-prove}, the fresh variables numbered by the tool)
\begin{align*}
&\forall n, v, a.\ 0 \le n \Rightarrow \forall a', i', n_4{:}\mathsf{Nat}, K, I, A.\\
&\quad K = \cnt(0, 1, n_4)\\
&\quad \wedge\ I = \tr{0}{\bl{K}}{i, k :: i + 1}\\
&\quad \wedge\ A = \tr{a}{\bl{K}, \bl{I}}{a', k, i :: a'[i := v]}\\
&\quad \wedge\ a' = \cur(A)\ \wedge\ i' = \cur(I)\\
&\quad \wedge\ \al{\bl{K}, \bl{A}, \bl{I}}{k, a', i :: i < n}\\
&\quad \wedge\ 0 \le \intf(n_4)\\
&\quad \Rightarrow \neg(i' < n) \Rightarrow \forall k.\ 0 \le k < n \Rightarrow a'[k] = v
\end{align*}
Read it line by line; every construct of the approach appears once.

\paragraph{The number of iterations.} $n_4$ is a natural number, the number of times the body runs. Nothing is
known about it except that it is some natural (its integer value $\intf(n_4)$ is nonnegative, stated explicitly
since the arithmetic works on integers). The loop test does not determine it directly; it is constrained by the
iteration constraint below.

\paragraph{The counter.} $K = \cnt(0, 1, n_4)$ is the sequence $0, 1, \ldots, n_4$, a trace of $n_4 + 1$ integers:
the iteration numbers. Every loop gets such a counter, and the lemmas of the database are indexed by it.

\paragraph{Traces.} A trace of type $\mathsf{Trace}\langle T\rangle$ is a nonempty sequence of values of type $T$,
the values of some quantity at the loop head before each iteration and after the last. Two functions take it
apart: $\bl{X}$ (``butlast'', written with floor brackets in the Dafny files too) is the list of all but
the last element, i.e.\ the values before each of the $n$ iterations, and $\cur(X)$ is the last element, the value
after the loop. The $j$-th element of a list is $\ear(j, \bl{X})$, with $j$ a natural number.

\paragraph{The trace of a variable.} $I$ is the trace of the index, written with the combinator
\[
\tr{x_0}{\bl{K}}{x, k :: u}
\]
It starts with $x_0 = 0$, the value before the first iteration, and for each iteration $k$ of the counter its next
value is the update $u$ applied to the previous value $x$. The combinator is a fold: $I$ has one element more than
$\bl{K}$, and
\[
\cur(\tr{x_0}{\bl{K}}{x, k :: u}) = u(\cdots u(u(x_0, 0), 1) \cdots, n_4 - 1).
\]
The array reads the index, so its trace $A$ has the history $\bl{I}$ as a further dependency, and its update reads
the index of the same iteration through the bound variable $i$: in iteration $k$, $i$ is $\ear(\natf(k), \bl{I})$,
the value of the index before that iteration. This is how the traces of a loop refer to each other: never to each
other's accumulators, only to the histories of the variables summarized before them.

\paragraph{Which variables share a trace.} The variables of a loop are partitioned by the strongly connected
components of their read relation (a variable reads the variables in its result, and those in the branch
conditions if the body branches), ordered so that each component comes after the ones it reads. A variable in no
cycle gets a trace of its own, as here. Variables that read each other get one trace with several accumulators,
which the second example shows; since the component graph is acyclic, no trace ever depends on itself through
another, and every trace is a closed term over the number of iterations and the earlier histories.

\paragraph{The exit values.} After the loop, the program variables are the final values of their traces,
$a' = \cur(A)$ and $i' = \cur(I)$, and the loop was left because its test failed, $\neg(i' < n)$.

\paragraph{The iteration constraint.} $\al{\bl{K}, \bl{A}, \bl{I}}{k, a', i :: i < n}$ states that the loop test
held before every iteration: the combinator $\mathsf{invs}$ ranges over the histories in parallel, binding the
iteration number $k$ and the values of the variables at position $k$, and requires its body for all positions. This
is the only place where the number of iterations is pinned down: the test must hold $n_4$ times and fail afterwards.

Nothing in this condition is specific to the program but the updates and the test; the rest is the schema that every
loop gets. In particular there is no invariant.

\subsection{The lemma database}

The engine does not know what a counter or a store is; it knows rewrite rules. A rule is a lemma with the attribute
\lstinline|{:rw}| whose conclusion is an equation $l = r$ (or an equivalence), read from left to right, possibly
with preconditions as side conditions. The variables of the lemma are matched against the goal. The database of
\texttt{-teq-state} is one Dafny file, \texttt{resources/cuvee/teq/state.dfy}, with the definitions of the types and
functions above and about forty lemmas. The ones this example needs:
\begin{lstlisting}
lemma {:rw} counter_def(i: int, c: int, n: Nat)
  ensures trace(i, for ⌊counter(0, 1, n)⌋ do x, k :: x + c) == counter(i, c, n)

lemma {:rw} current_counter(i: int, c: int, n: Nat)
  ensures current(counter(i, c, n)) == i + integer(n) * c

lemma {:rw} earlier_counter(k: Nat, i: int, c: int, n: Nat)
  ensures earlier(k, ⌊counter(i, c, n)⌋) == i + integer(k) * c

lemma {:rw} invs_counter_upper_nonnegative(m: int, n: Nat)
  requires 0 <= m
  ensures invs(for ⌊counter(0, 1, n)⌋ check k :: k < m) <==> integer(n) <= m

function {:fold} stores<a, b>(a: array<a, b>, keys: List<a>, values: List<b>): Trace<array<a, b>>
{ trace(a, for keys, values do b, k, v :: b[k := v]) }

lemma {:rw} maps_const<a>(x: a, i: int, c: int, n: Nat)
  ensures maps(for ⌊counter(i, c, n)⌋ yield v :: x) == ⌊consts(n, x)⌋

lemma {:rw} current_stores<a, b>(k: a, a: array<a, b>, keys: List<a>, values: List<b>)
  ensures current(stores(a, keys, values))[k]
    == if occurs(k, keys) then earlier(indexof(k, keys), values) else a[k]

lemma {:rw} occurs_counter_up(j: int, i: int, n: Nat)
  ensures occurs(j, ⌊counter(i, 1, n)⌋) <==> i <= j < i + integer(n)

lemma {:rw} indexof_counter_up(j: int, i: int, n: Nat)
  requires i <= j < i + integer(n)
  ensures indexof(j, ⌊counter(i, 1, n)⌋) == natural(j - i)

lemma {:rw} earlier_consts<a>(k: Nat, n: Nat, x: a)
  ensures earlier(k, ⌊consts(n, x)⌋) == x
\end{lstlisting}
Three kinds of lemma appear. \emph{Introduction} lemmas recognize a loop shape and name it: a trace that adds a
constant is a counter (\lemma{counter\_def}); a trace that stores values at keys is $\stores(a, keys, values)$,
which is a function definition marked \lstinline|{:fold}|, i.e.\ its body is rewritten \emph{to} the function.
\emph{Acceleration} lemmas give the closed form of a named shape: the final value of a counter, its $k$-th value,
the element of a store sequence at a key (\lemma{current\_stores}: the last value stored there, or the original
if the key was never stored). \emph{Bookkeeping} lemmas relate the list functions: $\occurs$, $\indexof$, $\prefix$,
the constant list $\consts$, and the third combinator $\mapc{xs}{x :: e}$, the list of $e$ for each element of $xs$,
which the engine introduces itself when a lemma needs a sequence of values that the program computes implicitly.

These lemmas are proved once, in Lean, from the recursive definitions; the program proof trusts them.

\subsection{The proof}

The engine simplifies the goal under a context of facts, innermost subterms first, and after each round applies the
first rule whose left-hand side matches and whose side conditions hold. Every rewrite step can be printed
(\texttt{-debug rewrite}); what follows is that printout, cleaned up. One idea appears along the way that is not in
the condition itself: the context of a combinator.

\paragraph{The index is a counter.} The trace of the index is matched by \lemma{counter\_def} as it stands:
\[
\tr{0}{\bl{K}}{i, k :: i + 1} \rw \cnt(0, 1, n_4).
\]
From here on $I$ is known to be a counter: the equation $I = \cnt(0, 1, n_4)$ is a fact of the context, and
whenever a lemma asks for a counter where the goal has $\bl{I}$, the engine follows the equation.

\paragraph{The index read by the array is the iteration number.} To simplify the update of $A$ the engine builds the
\emph{context of the combinator}: inside $\mathsf{for}\ \bl{K}, \bl{I}\ \mathsf{do}\ a', k, i$, the bound variable
$k$ is a value of $\bl{K}$, so $0 \le k < \intf(n_4)$, and $i$ is the value of $\bl{I}$ at position $k$,
$i = \ear(\natf(k), \bl{I})$. That read is simplified in the same context,
\[
\ear(\natf(k), \bl{I}) \rw 0 + \intf(\natf(k)) \cdot 1 \rw k,
\]
by \lemma{earlier\_counter} through the equation of $I$ and by $\intf(\natf(k)) = k$ for $0 \le k$. So in every
iteration $k$ the index is $k$, and the update of $A$ becomes $a'[k := v]$: ``the loop stores at $i$'' has become
``the loop stores at $0, 1, \ldots$''. The unused dependency $\bl{I}$ is dropped from $A$.

\paragraph{The array is a sequence of stores.} The trace $\tr{a}{\bl{K}}{a', k :: a'[k := v]}$ is matched by the
body of $\stores$ with $keys = \bl{K}$ and the values a sequence that the program never names: the engine
synthesizes it as the map of the stored expression over the iterations,
\begin{align*}
\tr{a}{\bl{K}}{a', k :: a'[k := v]} &\rw \stores(a, \bl{K}, \mapc{\bl{K}}{k :: v}) \\
\mapc{\bl{K}}{k :: v} &\rw \bl{\consts(n_4, v)}
\end{align*}
by the fold and \lemma{maps\_const}. The final array $a' = \cur(A)$ is therefore
\[
\cur(\stores(a, \bl{K}, \bl{\consts(n_4, v)})),
\]
the array after storing $v$ at each key of the counter, and the final index is
\[
\cur(\cnt(0, 1, n_4)) \rw \intf(n_4)
\]
by \lemma{current\_counter}.

\paragraph{The number of iterations is $n$.} The iteration constraint has become
$\al{\bl{K}}{k :: k < n}$ after the index read was evaluated, and \lemma{invs\_counter\_upper\_nonnegative} turns
it into $\intf(n_4) \le n$ (its side condition $0 \le n$ is the precondition). The exit $\neg(i' < n)$ with
$i' = \intf(n_4)$ gives $n \le \intf(n_4)$, and the arithmetic of the context concludes $\intf(n_4) = n$. The engine
records this as $n_4 = \natf(i')$ and replaces $\intf(n_4)$ by $i'$ from here on (the rewrite \lemma{integer\_eq}
in the log).

\paragraph{The postcondition.} Finally $a'[k]$ for $0 \le k < n$: $a'$ is a variable whose definition in the context
is $\cur(A)$ with $A$ the store sequence, and \lemma{current\_stores} fires through both,
\begin{align*}
a'[k] &\rw \mathsf{if}\ \occurs(k, \bl{K})\ \mathsf{then}\ \ear(\indexof(k, \bl{K}), \bl{\consts(n_4, v)}) \\
&\qquad\ \mathsf{else}\ a[k] \\
\occurs(k, \bl{K}) &\rw 0 \le k < 0 + \intf(n_4) \qquad\text{true, since } \intf(n_4) = n \\
\indexof(k, \bl{K}) &\rw \natf(k - 0) \\
\ear(\natf(k), \bl{\consts(n_4, v)}) &\rw v
\end{align*}
by \lemma{occurs\_counter\_up}, \lemma{indexof\_counter\_up} and \lemma{earlier\_consts}. The conclusion $a'[k] = v$
is true, the goal is dropped. The whole run takes about two seconds, of which the JVM start is most.

The proof needed no fact about the loop except what the database knows about counters, stores and constant lists.
Had the program stored $v$ at $2i$ or counted down, other lemmas of the same database would have fired.

\section{The element-wise exchange of two arrays}

\begin{lstlisting}
method swap(a: array<int, int>, b: array<int, int>, n: int)
  returns (a_: array<int, int>, b_: array<int, int>)
  requires 0 <= n
  ensures forall k: int :: 0 <= k < n ==> a_[k] == b[k] && b_[k] == a[k]
{
  var i: int;
  var t: int;
  a_ := a;
  b_ := b;
  i := 0;
  while i < n
  {
    t := a_[i];
    a_[i] := b_[i];
    b_[i] := t;
    i := i + 1;
  }
}
\end{lstlisting}

The modified variables are $t$, $a'$, $b'$ and $i$. The index reads nothing; the two arrays read each other, since
the new $a'$ stores a value of the old $b'$ and the new $b'$ a value of the old $a'$ (through $t$); the temporary
reads $a'$. The partition therefore gives three traces in this order: $I$ as before, one trace $S$ with the two
accumulators $a'$ and $b'$, and $T$ after it:
\begin{align*}
&I = \tr{0}{\bl{K}}{i, k :: i + 1}\\
&S = \mathsf{trace}(a, b,\ \mathsf{for}\ \bl{K}, \bl{I}\ \mathsf{do}\ a', b', k, i ::\ a'[i := b'[i]],\ b'[i := a'[i]])\\
&T = \tr{t_2}{\bl{K}, \bl{S}.0, \bl{I}}{t, k, a', i :: a'[i]}
\end{align*}
A trace of several accumulators has one initial value and one result per accumulator, and its values are read per
component: $\cur(S).0$ and $\cur(S).1$ are the final arrays, and the histories $\bl{S}.0$ and $\bl{S}.1$ are
ordinary lists, dependencies like any other, over which $T$ and the iteration constraint
$\al{\bl{K}, \bl{T}, \bl{S}.0, \bl{S}.1, \bl{I}}{k, t, a', b', i :: i < n}$ range. The rest of the condition has
the shape of the first example.

\subsection{Why this is the hard case}

In the paper on trace equation systems, a loop yields one trace per variable, and a variable that reads another has
the history of that other among its dependencies: $A' = \tr{a}{\bl{K}, \bl{B'}}{x, k, y :: x[k := y[k]]}$ and
symmetrically $B'$ over $\bl{A'}$. The two equations are recursive through each other. To summarize $A'$, the
engine needs $B'$ in closed form, which needs $A'$ in closed form. The paper resolves such cases by lemmas that tie
the two equations together, written per shape, and the summaries of the sorting algorithms in that line of work
carry a dozen side conditions each for this reason.

One trace for the cycle sidesteps the recursion: the two arrays are accumulators of a single fold, and the
per-variable traces, which the database lemmas are about, are its \emph{projections}, computed when a lemma asks for
one. The question is only how a projection may read the other component.

\subsection{The proof}

\paragraph{The index, as before.} $I$ becomes the counter, and in the context of the update of $S$ the read $i$ is
$k$, so both results store and read at position $k$.

\paragraph{The projection of $a'$ reads $b'$.} The postcondition asks for $\cur(S).0[k]$, a read of a component.
The engine projects $S$ to its component $0$: the trace of that accumulator alone, in which the other accumulator
becomes a bound variable over its own history,
\[
\pi_0(S) = \tr{a}{\bl{K}, \bl{I}, \bl{S}.1}{a', k, i, b' :: a'[k := b'[k]]}.
\]
This is a syntactic rearrangement, and a lemma about a trace with one accumulator matches it directly, with
$\bl{S}.1$ as a dependency the lemma may ignore. The fold of $\stores$ matches with the synthesized value sequence,
\[
\pi_0(S) \rw \stores(a, \bl{I}, \mapc{\bl{I}, \bl{S}.1}{k, b' :: b'[k]}),
\]
but that is not closed: the values stored are reads of $b'$. To know what $b'[k]$ is, the engine needs the element
$k$ of the other array in iteration $k$. In the context of the projection, $b' = \ear(\natf(k), \bl{S}.1)$, and
$\bl{S}.1$ is again a read of a component, whose normal form is the projection of $S$ to component $1$, simplified:
\[
\bl{S}.1 \rw \bl{\stores(b, \bl{I}, \mapc{\bl{I}, \bl{S}.0}{k', a' :: a'[k']})}.
\]
Its update reads component $0$ in turn. Here the engine would loop forever if it followed every read: the normal
form of component $0$ needs that of component $1$, which needs that of component $0$. The rule is that \emph{a
component is not projected inside its own normal form}: while component $0$ is being normalized, a read of $\bl{S}.0$
stays as it is, an inert dependency that the lemmas treat as an opaque sequence. So $a'[k']$ stays, and the normal
form of $b'$ is a sequence of stores whose values are unknown terms. That is enough, because of what is asked next.

\paragraph{Iteration $k$ reads a position that no earlier iteration wrote.} The lemma on an element of an earlier
value of a store sequence,
\begin{lstlisting}
lemma {:rw} earlier_stores<a, b>(k: a, j: Nat, a: array<a, b>, keys: List<a>, values: List<b>)
  ensures earlier(j, ⌊stores(a, keys, values)⌋)[k]
    == if occurs(k, prefix(j, keys)) then earlier(indexof(k, prefix(j, keys)), values) else a[k]
\end{lstlisting}
says: the value at $k$ after $j$ stores is the last value stored at $k$ among the first $j$ keys, or the original if
$k$ is not among them. Applied to the read $b'[k]$, with $j = \natf(k)$ and $keys = \bl{I}$,
\begin{align*}
b'[k] &\rw \ite{\occurs(k, \prefix(\natf(k), \bl{I}))}{\ear(\ldots)}{b[k]} \\
\prefix(\natf(k), \bl{I}) &\rw \bl{\cnt(0, 1, \natf(k))} \\
\occurs(k, \bl{\cnt(0, 1, \natf(k))}) &\rw 0 \le k < 0 + \intf(\natf(k)) \qquad\text{i.e. } k < k,\ \text{false}
\end{align*}
by \lemma{prefix\_counter} and \lemma{occurs\_counter\_up}. The first $k$ keys are $0, \ldots, k-1$, and $k$ is not
among them, so the \textsf{then} branch, and with it the opaque read of $a'$, disappears: in iteration $k$ the loop
reads the \emph{original} $b[k]$. This is the whole argument of the program's correctness, and the engine found it by
asking the right question (what is the element at $k$ of the earlier value) rather than by unfolding both arrays.

\paragraph{The closed forms.} With the read resolved, the projection of $a'$ no longer depends on $\bl{S}.1$, and
\begin{align*}
\cur(S).0 &\rw \cur(\stores(a, \bl{I}, \mapc{\bl{I}}{k :: b[k]})) \\
&\rw \cur(\stores(a, \bl{I}, \selects(b, \bl{I}))) \\
\cur(S).1 &\rw \cur(\stores(b, \bl{I}, \selects(a, \bl{I})))
\end{align*}
where $\selects(b, keys)$, the reads of $b$ at the keys, is another \lstinline|{:fold}| of the database. The number
of iterations is $n$ as before.

\paragraph{The postcondition.} $a'[k]$ for $0 \le k < n$ goes through the definition $a' = \cur(S).0$, its normal
form, and \lemma{current\_stores} as in the first example, now with the values $\selects(b, \bl{I})$:
\begin{align*}
a'[k] &\rw \mathsf{if}\ \occurs(k, \bl{I})\ \mathsf{then}\ \ear(\indexof(k, \bl{I}), \selects(b, \bl{I}))\ \mathsf{else}\ a[k] \\
&\rw \ear(\natf(k), \selects(b, \bl{I})) \rw b[\ear(\natf(k), \bl{I})] \rw b[k]
\end{align*}
by \lemma{earlier\_selects} and \lemma{earlier\_counter}; $b'[k] = a[k]$ is symmetric. About three seconds in all,
fourteen distinct lemmas, none written for the program, 160 rewrite steps and 16 normal forms of components.

\section{A binary search: a lemma about the whole loop}

The first two loops have closed forms: after $n$ iterations, the index is $n$ and the arrays are known element by
element. A binary search has none. How often it runs and where it ends depend on the contents of the array, and
what its correctness needs are \emph{bounds}: the lower end of the interval never passes the first occurrence of
$x$, and the upper end never passes the last one. The trace equation systems paper names this as the weak spot of
the approach, loops that need partial facts rather than closed forms. This section shows how the engine handles
such a loop with two further ideas: a lemma about a cycle of variables as a whole, here the bisection of an
interval, and facts that become available wherever their term occurs. Unlike in the first two examples, these
lemmas are not in the database yet. The file is \texttt{examples/dafny/state/bsearch\_bisect.dfy}; the run is the
same as before, and its output is again only the declarations.

\begin{lstlisting}
function sorted(ar: array<int, int>, len: int): bool

method search(a: array<int, int>, n: int, x: int) returns (i: int)
  requires 0 <= n && sorted(a, n)
  ensures 0 <= i ==> i < n && a[i] == x
  ensures i < 0 ==> forall k: int :: 0 <= k < n ==> a[k] != x
{
  var lo: int;
  var hi: int;
  var mid: int;
  lo := 0;
  hi := n;
  i := -1;
  while lo < hi
  {
    mid := (lo + hi) / 2;
    if a[mid] < x {
      lo := mid + 1;
    } else if x < a[mid] {
      hi := mid;
    } else {
      i := mid;
      break;
    }
  }
}
\end{lstlisting}
The predicate $\mathsf{sorted}(a, n)$, that $a[0..n)$ is nondecreasing, has no body; the proof uses it only through
the lemmas below.

\paragraph{The array by its partition points.} In a sorted segment $a[0..n)$, the elements below $x$ form a prefix
and those above $x$ a suffix. The file names the ends of these, $\mathsf{lower}(a, n, x)$ and
$\mathsf{upper}(a, n, x)$, as functions without a body, and states what they mean by three rules that turn a read
of the array into a comparison of indices:
\begin{lstlisting}
function lower(ar: array<int, int>, len: int, y: int): int
function upper(ar: array<int, int>, len: int, y: int): int

lemma {:rw} lower(ar: array<int, int>, len: int, y: int, m: int)
  requires sorted(ar, len) && 0 <= m && m < len
  ensures (ar[m] < y) <==> m < lower(ar, len, y)
lemma {:rw} upper(ar: array<int, int>, len: int, y: int, m: int)
  requires sorted(ar, len) && 0 <= m && m < len
  ensures (y < ar[m]) <==> upper(ar, len, y) <= m
lemma {:rw} equal(ar: array<int, int>, len: int, y: int, m: int)
  requires sorted(ar, len) && 0 <= m && m < len
  ensures (ar[m] == y) <==> lower(ar, len, y) <= m && m < upper(ar, len, y)
\end{lstlisting}
Sortedness is used here and nowhere else. The variable $len$ occurs only in the condition; it is bound by matching
$\mathsf{sorted}(ar, len)$ against the precondition. A forward lemma, \lemma{bounds}, states
$0 \le \mathsf{lower} \le \mathsf{upper} \le len$ wherever a partition point occurs. The rules hold only within the
array, for $0 \le m < len$: a read at an index whose range the context does not know stays a read.

The midpoint needs no rule: the arithmetic of the engine bounds an integer division by a constant,
$2 \cdot ((h + l)/2) \le h + l \le 2 \cdot ((h + l)/2) + 1$, which gives $l \le (h + l)/2$ if $l \le h$, and
$(h + l)/2 < h$ if $l < h$.

\subsection{The verification condition}

The modified variables are $lo$, $hi$, $mid$ and $i$. Since the body branches, every variable reads the variables
of the branch conditions, which read $lo$ and $hi$ through the midpoint. So $lo$ and $hi$ read each other and form
one trace $S$ with two accumulators. The traces of $mid$ and $i$ read $S$ and come after it. Writing $m$ for
$(lo + hi)/2$ and leaving out the trace of $mid$, which the goal does not need, the condition is
\begin{align*}
&S = \mathsf{trace}(0, n,\ \mathsf{for}\ \bl{K}\ \mathsf{do}\ lo, hi, k ::\\
&\qquad \mathsf{case}\ a[m] < x \Rightarrow m + 1\ \ \mathsf{case}\ \neg(a[m] < x) \wedge x < a[m] \Rightarrow lo,\\
&\qquad \mathsf{case}\ a[m] < x \Rightarrow hi\ \ \mathsf{case}\ \neg(a[m] < x) \wedge x < a[m] \Rightarrow m)\\
&I = \tr{-1}{\bl{K}, \bl{S}.0, \bl{S}.1}{i, k, lo, hi ::\\
&\qquad \mathsf{case}\ a[m] < x \Rightarrow i\ \ \mathsf{case}\ \neg(a[m] < x) \wedge x < a[m] \Rightarrow i}\\
&\al{\bl{K}, \ldots, \bl{S}.0, \bl{S}.1, \bl{I}}{k, \ldots, lo, hi, i ::\\
&\qquad lo < hi \wedge (a[m] < x \vee \neg(a[m] < x) \wedge x < a[m])}
\end{align*}
together with $lo' = \cur(S).0$, $hi' = \cur(S).1$ and $i' = \cur(I)$, under the precondition $0 \le n$ and
$\mathsf{sorted}(a, n)$. The path through \lstinline|break| is not a case of any update: the guards of a trace need
not cover every case, and the iteration constraint states that every iteration took one of the paths that
continue. The path that breaks appears only in the goal, as the last iteration. The goal has two parts:
\begin{itemize}
\item \emph{The exit}: if $\neg(lo' < hi')$, then the postcondition holds for $i'$.
\item \emph{The found case}: if $lo' < hi'$, $\neg(a[m'] < x)$ and $\neg(x < a[m'])$, then it holds for
  $i = m'$, where $m' = (lo' + hi')/2$.
\end{itemize}

There is no closed form to aim for. The values of $lo$ and $hi$ after the loop are not a function of the number
of iterations, and that number is not a function of $n$ alone. Writing $P$ for $\mathsf{lower}(a, n, x)$ and $Q$
for $\mathsf{upper}(a, n, x)$, the proof needs the bounds $0 \le lo' \le P$ and $Q \le hi' \le n$, and $i' = -1$.
These are the invariant that a Hoare-style proof would state. Here a lemma about the shape of the loop states it,
once for every loop of that shape.

\subsection{A lemma about the bisection}

$S$ is a bisection of the interval $[0, n)$: in each iteration, a probe strictly inside the interval is tested,
and $lo$ moves above it or $hi$ down to it. The file names such a trace, with the initial interval, the iterations,
the probe $M$ and the two guards $G$ and $H$ as arguments, by a function without a body and a rule that introduces
it:
\begin{lstlisting}
function bisection(l0: int, h0: int, ks: List<int>, M: (int, int) -> int,
                   G: int -> bool, H: int -> bool): Trace<(int, int)>

lemma {:rw} bisection(l0: int, h0: int, i: int, c: int, m: Nat,
                      M: (int, int) -> int, G: int -> bool, H: int -> bool)
  ensures trace(l0, h0, for ⌊counter(i, c, m)⌋ do lo, hi, k ::
          case G(M(lo, hi)) && lo < hi => M(lo, hi) + 1
          case H(M(lo, hi)) && lo < hi => lo,
          case G(M(lo, hi)) && lo < hi => hi
          case H(M(lo, hi)) && lo < hi => M(lo, hi))
    == bisection(l0, h0, ⌊counter(i, c, m)⌋, M, G, H)
\end{lstlisting}
The pattern is a trace of two accumulators, matched against $S$ as a whole, component by component. $M$, $G$ and
$H$ are higher-order pattern variables. The conjunct $lo < hi$ is not in the program's guards; it must follow from
them in the context of the update, which has the iteration constraint. So the name stands only for iterations of a
loop with the test $lo < hi$.

What a bisection keeps is stated with the \emph{cut} of a guard: for a predicate $G$ that holds on a prefix of
$[l, h)$, $\mathsf{cut}(G, l, h)$ is the first index where it fails, a function without a body. A predicate $H$
that holds on a suffix has the cut of its negation, the first index where $H$ holds. Two forward lemmas give the
bounds:
\begin{lstlisting}
lemma {:fw} bisection_lo(l0: int, h0: int, ks: List<int>, M: (int, int) -> int,
                         G: int -> bool, H: int -> bool)
  requires l0 <= h0
  requires forall l: int, h: int :: l < h ==> l <= M(l, h) && M(l, h) < h
  requires forall p: int, q: int :: l0 <= p && p <= q && q < h0 && G(q) ==> G(p)
  ensures l0 <= current(bisection(l0, h0, ks, M, G, H)).0 <= cut(G, l0, h0)

lemma {:fw} bisection_hi(l0: int, h0: int, ks: List<int>, M: (int, int) -> int,
                         G: int -> bool, H: int -> bool)
  requires l0 <= h0
  requires forall l: int, h: int :: l < h ==> l <= M(l, h) && M(l, h) < h
  requires forall p: int, q: int :: l0 <= p && p <= q && q < h0 && H(p) ==> H(q)
  ensures cut((j: int) => !H(j), l0, h0) <= current(bisection(l0, h0, ks, M, G, H)).1 <= h0
\end{lstlisting}
If the probe lies strictly inside the interval and $G$ holds on a prefix, $lo$ stays within $l_0$ and the cut of
$G$: it passes a probe only where $G$ holds, hence on all indices up to it. Dually for $hi$. The lemmas say nothing
about arrays, and nothing about the midpoint: any probe strictly inside the interval will do, e.g.\ the probe
$lo + (hi - lo)/2$, which does not overflow (\texttt{bsearch\_safe.dfy}, the same lemmas). On a sorted array, the
cut of the comparison with $y$ is the partition point:
\begin{lstlisting}
lemma {:rw} cut_lower(ar: array<int, int>, len: int, y: int)
  requires sorted(ar, len) && 0 <= len
  ensures cut((j: int) => ar[j] < y, 0, len) == lower(ar, len, y)

lemma {:rw} lower_succ(ar: array<int, int>, len: int, y: int)
  requires sorted(ar, len)
  ensures lower(ar, len, y + 1) == upper(ar, len, y)
\end{lstlisting}
The second rule is the other partition point: on the integers, $\neg(y < ar[j])$ is $ar[j] < y + 1$.

Why forward lemmas and not rewrite rules: the goal speaks about $lo'$ and $hi'$, and none of its terms is a
comparison of the form $\cur(\mathsf{bisection}(\ldots)).0 \le \mathsf{cut}(\ldots)$. A rewrite rule fires only where
its left-hand side occurs, so a rule on the comparison would never fire. A forward lemma is assumed wherever a term
matching its \emph{trigger}, here $\cur(\mathsf{bisection}(\ldots)).0$, occurs in a fact that the traversal assumes.
The instance is stated over the term as it occurs, so the bound reaches the arithmetic of the goal.

\subsection{The proof}

\paragraph{The loop is a bisection.} Where the traversal simplifies the definition of $S$, the rule
\lemma{bisection} matches it. The result of the first case, $m + 1$, binds the probe,
$M = (lo, hi) \Rightarrow (hi + lo)/2$. The guards are then matched with the probe in place:
$G((hi + lo)/2)$ against $a[m] < x$ binds $G = (z) \Rightarrow a[z] < x$ by abstracting the probe, and $H$ likewise to
$(z) \Rightarrow x < a[z]$. In the context of the update, the histories $\bl{S}.0$ and $\bl{S}.1$ stand for the
accumulators, so the iteration constraint gives $lo < hi$, and the conjuncts $lo < hi$ of the pattern hold. Then
\[
S = \mathsf{bisection}(0, n, \bl{\cnt(0, 1, n_8)}, (lo, hi) \Rightarrow (hi + lo)/2,
(z) \Rightarrow a[z] < x, (z) \Rightarrow x < a[z]).
\]

\paragraph{The bounds as forward facts.} Where the traversal assumes $lo' = \cur(S).0$, the trigger of
\lemma{bisection\_lo} matches $\cur(S).0$ through the definition of $S$. Its conditions are closed now and are
decided. The probe condition $l < h \Rightarrow l \le (h + l)/2 < h$ follows from the bounds of the division. That $G$
holds on a prefix is
\[
\forall p, q.\ 0 \le p \le q < n \wedge a[q] < x \Rightarrow a[p] < x,
\]
which the rules on sortedness decide within the range of the premise: $a[q] < x \rw q < P$ and $a[p] < x \rw p < P$,
and $p \le q < P$ gives $p < P$. The instance is simplified before it is assumed, which rewrites the cut by
\lemma{cut\_lower}; for \lemma{bisection\_hi}, the negation $\neg(x < a[j])$ becomes $a[j] < x + 1$, whose cut is
$\mathsf{lower}(a, n, x + 1)$ by \lemma{cut\_lower} and $Q$ by \lemma{lower\_succ}:
\begin{align*}
&0 \le \cur(S).0 \le P &&\text{by \lemma{bisection\_lo}},\\
&Q \le \cur(S).1 \le n &&\text{by \lemma{bisection\_hi}}.
\end{align*}

\paragraph{The index $i$ stays $-1$.} Once its guards are evaluated, both cases of $I$ keep $i$, so the cases are
joined, the dependencies on $S$ are dropped, and
\[
\tr{-1}{\bl{K}}{i, k :: i} \rw \consts(n_8, -1), \qquad \cur(I) \rw -1
\]
by \lemma{consts\_def} and \lemma{current\_consts}; the reads of $i$ in the iteration constraint become $-1$ by
\lemma{earlier\_consts}.

\paragraph{The exit.} With $\neg(lo' < hi')$, i.e.\ $hi' \le lo'$, the context has
$hi' \le lo' \le P \le Q \le hi'$, where $P \le Q$ is the forward fact \lemma{bounds}, and the arithmetic
concludes $P = Q$. Since $i' = -1$, the first postcondition holds vacuously. In the second, the premise
$0 \le k < n$ is the range of \lemma{equal}, so $a[k] = x \rw P \le k < Q$, which is false for $P = Q$; hence
$a[k] \ne x$ for every $k$.

\paragraph{The found case.} Here $0 \le lo' < hi' \le n$ puts $m'$ within the array, and the branch conditions
give $\neg(m' < P)$ and $\neg(Q \le m')$, so $P \le m' < Q$. Then $a[m'] = x \rw P \le m' < Q$ holds, $m' < n$
follows from $Q \le n$, and $m' < 0$ is false.

The run uses twelve lemmas: all nine of the file and three of the database on constant traces. The log has 253
rewrite steps, 49 of them views of components, and the run takes about 8 seconds, 18 on a single core.

\subsection{What this example shows, and what it does not}
\label{sec:missing}

\paragraph{A partial description is enough.} The proof never computes $lo'$ or $hi'$. The trace of the cycle is
named by the shape of its loop and described by the bounds that the shape guarantees, and the bounds are available
wherever the goal mentions the variables. This is the form a description takes when the loop has no closed form,
and it uses the representation unchanged: the cycle is the same kind of trace as in the swap, matched as a whole.

\paragraph{A lemma about a cycle as a whole.} The invariant of the loop relates both variables, and the lemma about
the bisection states it at once, for the two accumulators together. Its shape is general: any pair of guards that
hold on a prefix and a suffix, any initial interval, any probe strictly inside it. The same lemmas prove the lower
bound of a sorted array (\texttt{examples/dafny/state/lower\_bound.dfy}), which the earlier form of the tool did not.
The lemmas are candidates for the database: the bisection and its cuts for searches in general, the partition
points for sorted arrays.

\paragraph{What is specific.} The rules on sortedness state what sortedness means for a comparison with a fixed
key; another use of sortedness, e.g.\ that a merge of two sorted arrays is sorted, needs other rules. The guards of
the program must be comparisons that these rules know, and the probe must be computed in the loop's update from
$lo$ and $hi$ alone.

\section{The engine, in short}

The examples used the following machinery, which the engine of \texttt{-prove} provides for every goal.

\begin{description}[leftmargin=1.5em]
\item[Contextual simplification.] The goal is traversed innermost first; at each position the context holds the facts
  that are known there (the antecedents of the implication, the other conjuncts, the guards of a branch), and a
  subformula known to hold or to fail is replaced by its truth value. Combinator bodies get the context of their
  position: the ranges of the bound variables and their values in the dependencies.
\item[Rewriting with the database.] After each round, the first rule whose left-hand side matches the term at the
  top and whose side conditions hold is applied. Matching is modulo the usual algebra of arithmetic, the binding
  structure of the combinators, and higher-order patterns for shapes with a free function in them. Side
  conditions that are closed after the match are looked up among the facts and otherwise decided by the same
  simplification; conditions with free variables are matched against the facts, which binds them.
\item[Definitions and classes.] Equations among the facts, $K = \cnt(0, 1, n_4)$ or $a' = \cur(S).0$, are kept
  in congruence classes. A variable that a pattern does not match is matched like each member of its class, so
  a lemma on counters applies to $\bl{K}$, and a lemma on stores applies to $a'$ through its definition and the view
  of that definition.
\item[Arithmetic.] Linear facts over the integers go to a simplex over the rationals with integer rounding, which
  decides the comparisons the examples needed ($\intf(n_4) = n$ from the two bounds, $k < k$ false). An integer
  division by a constant $c$ is an atom with the bounds $c \cdot (t/c) \le t \le c \cdot (t/c) + c - 1$, which place the
  midpoint of the binary search in its interval.
\item[Components of a cycle.] A read $\cur(S).i$ or $\bl{S}.i$ of a trace with several accumulators is matched
  structurally against the projection of $S$ to the component when the pattern has that shape, and otherwise modulo
  the normal form of the component, computed once per loop and component under the facts that mention its variables
  and memoized; a component is not projected inside its own normal form; a read whose normal form is closed is
  replaced by it in place. The histories $\bl{S}.j$ are never rewritten in place, which is what keeps the projections
  from unfolding each other.
\item[Forward facts.] A lemma marked \lstinline|{:fw}| is assumed wherever a term that matches its trigger (the term
  of its conclusion with the most variables) occurs in a fact the traversal assumes. The trigger is matched like
  the left-hand side of a rule, through definitions and views, and the instance names the term as it occurs; it is
  simplified by the rules before it is assumed, and it fires nothing itself, so this terminates.
\item[Cycles as a whole.] A pattern with several accumulators matches a trace of as many, component by component,
  in the context of the update, where the histories of the trace stand for its accumulators; a read $\cur(T).i$ of
  a pattern matches that of a variable through its definition. Higher-order patterns may be nested, $G(M(lo, hi))$:
  the inner one is bound first, and the argument of the outer one is then a term that is abstracted wherever it
  occurs.
\end{description}

The first two examples are proved by the earlier form of the tool (\texttt{-teq -simplify}, one trace per variable
without the partition) with the same lemmas; the swap needed there what the cycle trace avoids, the two equations
over each other's histories, resolved by following the equations through the context. The partition matters for
loops where the variables cannot be layered, and most of all for nested loops, where an inner loop becomes a single
value of the outer update rather than a family of fresh sequences, since no trace depends on another and all can be
substituted; those examples are in the same directory of the repository (\texttt{examples/dafny/state}, nested sums,
row sums, a transpose).

\section{What the examples do not show}

The first two programs have a layered loop: the index depends on nothing, the arrays depend on the index and on
each other only at the position being written. The database covers such loops without help. Programs whose loops
carry an accumulated property (a sorted prefix, a running maximum, a search that stops) need lemmas about their
shapes, some of them written for the program, and the engine has to match those lemmas against views whose shape
it has not seen before. The binary search is such a program, proved by a lemma about the bisection that is general
but not yet in the database. The open items at the time of writing:
\begin{itemize}
\item the bisection and the partition points of sorted arrays in the database;
\item lemmas about other cycles as a whole, e.g.\ for merging, where two pointers move by comparisons of the
  elements they point to, and sorting in this form;
\item which lemmas of the database should be forward facts rather than rewrite rules.
\end{itemize}
The record of the implementation, \texttt{ideas/deduction-engine-implementation.md} in the repository, keeps the
state of these.
